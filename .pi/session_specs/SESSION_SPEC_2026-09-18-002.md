# Nozzle 2: Tool surfacing

Execute directly. Do NOT delegate to heavy_think. Binding contract: VERIFYING.md.

## Frozen design

- Bundles: tools grouped by namespace in owner config (e.g. `browser_*`, `tavily_*`, `goal_*`,
  pins, whatsapp). The extension ships NO bundle opinions; config-only. Always-on core
  (read, write, edit, bash, grep, find, ls) is hardcoded and never routed.
- Scoring: one BATCHED Jev request per epoch (descriptions only, small question payloads),
  one Noul per configured namespace over the same digest built for Nozzle 1 (share the digest
  and the epoch boundary; do not build a second pipeline).
- Surfacing: namespace schemas included in the tool set only while active. Same frozen-epoch
  rule as skills. If tool-set mutation requires removing tools mid-epoch: forbidden; apply at
  boundary only.
- Degradation: Jev unreachable / key missing / repeated 429 → fail-static (all namespaces
  visible, exactly Pi default), one `ctx.ui.notify`, `ROUTE_DEGRADED: reason=…` log line.
- Escape hatch: if the model produces a tool name that was surfaced off, the extension detects
  the unknown-tool error and surfaces that namespace at the next boundary (miss-recovery path),
  logging `TOOL_SURFACE_MISS: namespace=…`.
- Telemetry: `TOOL_SURFACE: epoch=… active=[…] scores={…}` per epoch.

## Milestones

- M1: config schema (namespaces, core list, thresholds), batched scorer over shared digest,
  boundary-applied surfacing, unit tests with fixture Jev server.
- M2: fail-static paths, unknown-tool miss recovery, telemetry, VERIFYING §5 Nozzle-2 scenarios
  as passing tests.
